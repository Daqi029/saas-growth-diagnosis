# Pre-launch readiness

A product without meaningful users cannot be diagnosed by conversion benchmarks. The goal is to make it ready to learn quickly and avoid obvious value-path failures before traffic arrives.

## Inspect first

Use the repository, local app, preview deployment, public pages, specifications, and tests already available. Determine:

- who the first narrow customer is and what job they are trying to complete;
- what promise brings them to the product;
- the shortest path from arrival to a real result;
- the candidate Aha Moment and whether it is measurable;
- what the first empty state contains;
- which steps are required before value and which can be deferred;
- where pricing or a paid boundary appears;
- what truthful trust evidence exists;
- whether analytics can reconstruct the first-use funnel after launch.

## Readiness checks

### Value-path readiness

- Can a target user understand the product and next action quickly?
- Does the first session produce a concrete result rather than only setup?
- Is there a prefilled example, template, demo data, or guided task where blank-state anxiety is likely?
- Can optional profile, team, integration, and preference steps wait until after value?

### Measurement readiness

At minimum, define events for:

```text
qualified entry
→ primary CTA
→ signup completed
→ first-use started
→ candidate value event completed
→ upgrade intent
→ purchase completed
→ first natural return
```

For each event, check identity continuity, timestamp, acquisition source, product segment, plan or trial state, and the event property needed to distinguish a real result from a shallow click.

Do not prescribe every event imaginable. Instrument the decisions the team expects to make during the first launch cycle.

### Learning-plan readiness

Define before launch:

- first target cohort and acquisition source;
- one primary activation hypothesis;
- one qualitative observation method such as session review or interviews;
- a daily quality check for broken tracking and severe blockers;
- a cohort review point after enough time has elapsed;
- what evidence would cause the team to change the onboarding or positioning hypothesis.

## Pre-launch deliverable

Return:

1. readiness verdict: ready to learn / launchable with risks / not yet observable;
2. three highest risks before first value;
3. candidate Aha Moment and its uncertainty;
4. minimum event and cohort plan;
5. three changes worth making before launch;
6. issues that should wait for real user evidence;
7. one immediate action.

Do not claim the product has a traffic, conversion, activation, or retention problem without real user behavior. Call these risks or hypotheses.
